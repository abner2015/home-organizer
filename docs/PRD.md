# PRD — AI 家庭收纳管家

> Product Requirements Document · 第一版（Web）

---

## 1. 产品定义

**AI 家庭收纳管家** 是一个帮助家庭成员管理物品存放位置的产品。用户先建立家庭空间模型（家 / 房间 / 柜子 / 层 / 格），每件新物品入库时拍照 + 文字描述，系统自动识别物品、提取属性、结合空间模型和收纳规则，推荐具体存储位置。

最终产品形态：微信小程序 + 后端 API + AI Agent。
**第一阶段**：交付一个 Web 版（Next.js）用于快速验证产品假设，再迁移到小程序。

---

## 2. 用户与场景

### 2.1 用户角色

| 角色 | 描述 |
| --- | --- |
| 家庭主账号 | 第一个注册的成员，拥有家庭空间、规则、偏好的完整管理权 |
| 家庭成员 | 受邀加入家庭，可查看空间、记录物品、查看推荐 |
| 访客 | 仅查看自己被分享的物品或区域（第二版考虑） |

第一版只实现"主账号 + 家庭成员"两种角色，共享同一个家庭视图。

### 2.2 核心场景

1. **建立家庭空间** — 首次使用创建"家"，添加房间，为每个房间添加柜子/架子/抽屉，并逐层、逐格定义具体的 `StorageSlot`。
2. **录入新物品** — 上传物品照片 + 可选文字描述，系统识别物品并给出存储建议。
3. **查看与确认推荐** — 用户看到候选位置（1～3 个），可一键确认、修改或否决。确认后生成 `ItemPlacement`。
4. **查找物品** — 输入名称 / 拍照，查询物品当前所在位置。
5. **整理与回溯** — 浏览家庭空间、查看某个柜子里所有物品、查看历史摆放记录。
6. **调整规则** — 添加 / 修改 `HomeRule`（如"厨房不放化学品"、"药品必须上锁"），影响后续推荐。

### 2.3 关键用户流程

**首次使用 → 第一次推荐**

1. 注册 → 创建家 → 添加至少 1 个房间
2. 在房间内添加至少 1 个 StorageUnit（柜子 / 架子 / 抽屉柜）
3. 为 StorageUnit 添加至少 1 个 Section（层 / 抽屉 / 收纳盒）
4. 为 Section 添加至少 1 个 Slot（格）
5. 点击"录入新物品"→ 上传照片 → 系统返回 1～3 个推荐 Slot
6. 用户确认 / 修改 → 生成 ItemPlacement

**已有家庭 → 录入新物品**

1. 进入首页 → 点击"录入新物品"
2. 上传照片 + 可选文字描述
3. 系统返回：识别结果、属性、推荐 Slot（含置信度、依据）
4. 用户确认 → 生成 ItemPlacement；如拒绝，可手动搜索位置后记录

## 3. 功能需求

### 3.1 家庭空间管理

- F-1.1 创建 / 编辑 / 删除 `Home`。
- F-1.2 在 Home 下创建 / 编辑 / 删除 `Room`。
- F-1.3 在 Room 下创建 / 编辑 / 删除 `StorageUnit`（类型：柜子 / 架子 / 抽屉柜 / 收纳盒 / 其他自定义）。
- F-1.4 在 StorageUnit 下创建 / 编辑 / 删除 `StorageSection`（类型：层 / 抽屉 / 收纳盒）。
- F-1.5 在 StorageSection 下创建 / 编辑 / 删除 `StorageSlot`（具体到"哪一格"）。
- F-1.6 支持层级展示（Home → Room → Unit → Section → Slot 树形视图）。
- F-1.7 Slot 支持容量字段（体积、重量、是否敏感物品专用）。

### 3.2 物品管理

- F-2.1 创建 Item（图片 + 文字描述 + 元数据：分类、品牌、尺寸、敏感标记等）。
- F-2.2 Item 图片存到 MinIO，DB 仅存引用与缩略图 URL。
- F-2.3 Item 可在多个 Slot 中存在不同时间段的 `ItemPlacement`（支持历史回溯）。
- F-2.4 查询物品：按名称 / 类别 / 上传时间 / 当前 Slot 检索。
- F-2.5 删除 Item：必须先解除所有 active `ItemPlacement`。

### 3.3 AI 识别与推荐

- F-3.1 Vision：上传图片后调用多模态模型，得到结构化识别结果（名称、类别、属性、尺寸估计、敏感标记等）。
- F-3.2 推荐：基于"物品 + 家庭空间 + HomeRule + 历史 + 用户偏好"生成 1～3 个候选 Slot，含依据与置信度。**推荐流程分层**：先做确定性候选生成（从全部 Slot 缩到 ≤ 20）→ 硬规则约束过滤 → 确定性 Ranking → LLM 对 surviving 候选精排 + 写理由。LLM 不参与候选生成或约束过滤。
- F-3.3 推荐必须经过 Verifier（最终安全网）；Verifier 失败可 Retry LLM（最多 2 次）。Vision 阶段独立 parse-retry ≤ 2 次。
- F-3.4 用户可对推荐结果做"接受 / 调整 / 否决"反馈，反馈写回训练/调优数据。
- F-3.5 全部 AI 调用记录到 `AgentTrace`，含 9 步 pipeline 完整步骤与每步 payload。
- F-3.6 冷启动：新用户（无历史 / 无偏好）由 `default_room_map` 提供兜底映射，确保仍能给出 top 候选。

### 3.4 规则与偏好

- F-4.1 `UserPreference`：个人偏好（如"我常把工具放在车库"）。
- F-4.2 `HomeRule`：家庭级规则（"厨房不放过期食品"、"药品上锁"），由自然语言 + 结构化字段描述。
- F-4.3 规则在推荐时作为硬约束或软权重。

### 3.5 会话与对话（第二版强化）

- F-5.1 第一版：单轮（一次图片 → 一次推荐）。
- F-5.2 第二版：支持多轮对话（`Conversation` + `AgentTrace`），用户可追问"换一个大一点的格子"、"放到易拿取的位置"等。

## 4. 非功能需求

- NFR-1 **性能**：单次识别 + 推荐 P95 ≤ 8s；纯查询 P95 ≤ 300ms。
- NFR-2 **可用性**：核心 API 99.5% 可用；图片上传失败可重试。
- NFR-3 **可观测**：所有 AI 调用、推荐请求、错误都有 trace 和日志。
- NFR-4 **安全**：API Key 仅存于后端 `.env`；MinIO / PostgreSQL 不暴露公网；图片上传走预签名 URL。
- NFR-5 **可移植**：单条 `docker compose up` 启动完整系统（PostgreSQL、Redis、MinIO、API、Web、Nginx）。
- NFR-6 **国际化**：第一版仅中文。
- NFR-7 **可测试**：所有核心功能有单元/集成/Agent 测试覆盖。
- NFR-8 **数据迁移**：所有 DB schema 变更通过 Alembic。

## 5. MVP 边界

### 5.1 第一版必须做（In）

- 注册 / 登录（邮箱 + 密码即可，第一版不做 OAuth / 短信）
- Home / Room / StorageUnit / StorageSection / StorageSlot 完整 CRUD
- Item 上传（图片 + 描述）+ Vision 识别
- AI 推荐（含 Verifier、Retry）
- 推荐确认 → ItemPlacement 落库
- 物品搜索
- AgentTrace 记录
- Docker Compose 一键启动
- 关键指标埋点（见 `docs/EVALUATION.md`）

### 5.2 第一版不做（Out）

- 微信小程序
- 多轮对话
- 多人协作 / 权限细分
- 物品图像相似度检索（先用文本搜索）
- pgvector / 语义搜索
- 计费 / 套餐
- 离线模式
- 国际化 / 多语言

### 5.3 第二版候选

- 微信小程序
- 多轮对话与对话历史
- 物品图像相似度搜索（pgvector）
- 家庭成员协作权限
- 收纳建议的"季节性"与"使用频率"感知
- 整理任务（chore）系统

---

## 6. 成功指标

详见 `docs/EVALUATION.md`。第一版关键目标：

- 推荐可被用户接受率 ≥ 60%
- 识别准确率（Top-1）≥ 75%
- Verifier 拦截错误推荐率 ≥ 90%
- Verifier 误拦截率 ≤ 5%
- P95 推荐耗时 ≤ 8s
- 单次 docker compose 启动成功率 ≥ 95%

---

## 7. 风险与开放问题

| 风险 | 应对 |
| --- | --- |
| 多模态模型识别不稳定 | 引入 Verifier + 兜底问题清单（"无法识别时向用户追问"） |
| 推荐结果用户不信任 | 提供"依据"（explanation），并在 UI 展示 |
| Slot 容量约束难建模 | 第一版只做"类型 + 软约束"，不做严格物理仿真 |
| 历史数据不足导致冷启动 | 引入"通用收纳知识"作为兜底（prompt 中的常识） |
| 微信小程序迁移成本 | 第一版用 Web，但保持 API 与数据结构无 Web 特定假设 |
