## 1. 产品定义

**AI 家庭收纳管家** 帮**不会收纳的人**做收纳规划与最终放置 —— 你不用请收纳专家也可以做到。

它要解决的不是「记录东西放在哪」，而是「**我到底该把它放哪**」。因此产品的重心不在于
让用户录入得更快，而在于**让系统替用户做判断**：用户只需要给出一件东西（一张照片、
一句话），系统告诉他具体到「哪个柜子、哪一层、哪一格」的位置，并说清楚为什么。

**目标用户**：个人与家庭都有。个人用户（租房、独居、学生）需要的是「东西多、地方小，怎么安排」；
家庭用户需要的是「一家人共用一套空间，别互相放乱」。

**最终形态**：微信小程序 + 后端 API + AI Agent。
**第一阶段**：Web 版（Next.js）用于快速验证产品假设，再迁移到小程序。API 与数据结构不含
任何 Web 特定假设。

### 1.1 核心价值：放 · 理 · 找

| | 用户的问题 | 产品给出的答案 |
| --- | --- | --- |
| **放** | 这件东西该放哪儿？ | 具体到柜 / 层 / 格的位置 + 一句人话理由。可以来自拍照识别，也可以来自用户已有的物品 |
| **理** | 我家是个什么状况？该怎么整理？ | 空间结构的描述（有几个柜子、还剩多少空位）、收纳规则、以及「整柜东西怎么归类」的建议 |
| **找** | 我那件东西放哪了？ | 自然语言问答（"雨伞在哪"）+ 位置回溯历史 |

三者共用同一套家庭空间模型与同一条推荐 pipeline。**「放」是核心，「理」是让用户建立信任的前置，
「找」是让用户愿意持续录入的回报。**

### 1.2 一句话验收

> 一个不会收纳的人，注册进来之后，**在不看说明书的情况下**能把一件东西放对地方，
> 并且知道为什么放那儿。

## 2. 用户与场景

### 2.1 用户角色与权限

| 角色 | 空间结构 | 物品 | 规则 / 偏好 | 成员管理 |
| --- | --- | --- | --- | --- |
| **家庭主账号**（owner） | 增删改 | 增删改 | 增删改 | 邀请 / 移除 |
| **家庭成员**（member） | 增删改 | 增删改 | 只读 | — |
| **访客**（第二版） | 只读 | 只读 | 只读 | — |

第一版实现 **owner + member** 两种角色，共享同一个家庭视图（尚未做「成员只能看自己物品」）。
成员管理接口（邀请 / 移除）**尚未实现**。

**技术口径（已实现，见 `docs/API.md` §1.2）**

- `Authorization: Bearer <jwt>` = **你是谁**（签名凭证，不可伪造）
- `X-Home-Id` = **你在哪个家操作**（只是选择器，**不是凭证**，每次请求重新校验 `HomeMembership`）
- 访问不属于自己的家 → **404，不是 403**（403 等于承认这个家存在）
- 注册时自动 provision 一个「我的家」+ owner 身份（否则新账号没有任何家可选，是死路）

### 2.2 三段旅程

产品的全部功能围绕三段旅程组织。**P0 只做这三段。**

#### 旅程 A — 拍照即建模（`P0.2`，✅ 已交付 2026-09-22）

> 「我有一堆东西和一个空房子，系统先帮我把家搭起来。」

1. 新账号注册 → 家是**空树**（此前产品的最大断点：结构只能靠命令行 seed 出来）
2. 用户拍一张柜子的照片 / 说一句「我家厨房有个三层的吊柜」
3. **AI 提议**结构（房间 / 柜子 / 层 / 格子）并展示给用户
4. **用户确认后**才写入数据库；未确认的提议不落库
5. 用户的家里从此有了可用的收纳位置，推荐、落位、「找」全都有了落脚点

入口：`/home/setup`（`StructureBuilder` = AI 提议流 + 手动搭建）。写接口见 `docs/API.md` §3–§5。

#### 旅程 B — 反向录入（`P0.3`，✅ 已交付 2026-09-22）

> 「这东西我早就知道该放哪，别让我走一遍 AI。」

1. 用户已经有明确的物品和明确的去向（例如「这些书放书柜第二层」）
2. 直接把物品放进指定 `StorageSlot` —— **不调用 LLM**，不走推荐（`POST /api/v1/placements`）
3. 支持连续补录多件：物品列表 / 详情页逐件「放到这里」（放完**不导航**），
   或 `/items/place`「批量归位」——先选一格，再勾选多件一次落位
4. 放错了可以「移出」——**软关闭**（`removed_at`），摆放历史仍可读

旅程 B 与旅程 A/推荐共用同一套 `ItemPlacement`，因此后续「找」和「理」照样能用。
写接口见 `docs/API.md` §8。

#### 旅程 C — 找（✅ 已交付）

> 「我那个充电线呢？」

- 自然语言查询（`POST /api/v1/search`）：找物品、找位置、判断有没有、列出某类、给出"放哪里"的建议
- 结构问答：「我家有几个柜子」「还有多少空位」由 `describe_storage` 意图 + `build_home_blueprint` 回答
- 有状态的多轮对话（回放最近 8 轮），助手能接住「那它旁边呢」这类追问
- 回答由聊天模型**从确定性草稿改写**而成；模型不可用时回退到草稿，不出现"AI 挂了就没有答案"

#### 贯穿三段：放（推荐） ✅ 已交付

拍照 / 描述 → 9 步 pipeline → 1～3 个候选 Slot（含理由）→ 用户接受 / 拒绝 / 调整。
接受后写 `ItemPlacement` 并落库。`P0.4` 会把「接受 / 拒绝」反馈回灌到偏好，让下一次更准。

### 2.3 使用指引

产品承诺「无需繁琐录入」，前提是用户**知道下一步该做什么**。指引不是帮助文档，而是长在界面里的：

| 场景 | 指引 |
| --- | --- |
| 刚注册、家是空树 | 空状态不显示「暂无数据」，而是给一个动作：**拍照即建模**（旅程 A） |
| 第一次进入推荐页 | 解释推荐从哪来：候选是怎么筛的、为什么是这个格子（讲理由，`P0.4`） |
| 不确定能问什么 | 助手页给出建议问题（已实现）；助手本身也能回答「你能做什么」 |
| 用户想自己来 | 每条 AI 路径旁都有「手动填写 / 我自己放」的出口（旅程 B） |

## 3. 功能需求

> 标注含义：**✅ 已实现** / **⏳ 待做（P0.x）** / **📋 设计稿（未排期）**

### 3.1 家庭空间管理

- ✅ 层级展示（Home → Room → Unit → Section → Slot 树形视图）、`GET /homes/{id}/space-tree`
- ✅ Slot 容量与类别约束字段（`capacity`、`allowed_categories` 参与候选生成与 Verifier）
- ⏳ **F-1.1** Home 的创建（当前由注册自动 provision；尚无显式创建接口）
- ✅ **F-1.2 / F-1.3 / F-1.4 / F-1.5** 在 Home 下创建 / 编辑 / 删除 Room、StorageUnit、StorageSection、StorageSlot
  （`P0.2` 已交付；删除有子级或有 placement 记录（含已 removed）的节点 → 409；非成员 → 404）
- ✅ **F-1.8**（新增）**AI 提议结构 + 用户确认**：AI 可以提议新建房间 / 柜 / 层 / 格，
  但**必须经用户显式确认后才写入数据库**；未确认的提议不得落库。
  见 `AGENTS.md` §3.3 的修订说明。

### 3.2 物品管理

- ✅ **F-2.1** 创建 Item（图片 + 文字描述 + 元数据：分类、品牌、尺寸、敏感标记）
- ✅ **F-2.2** Item 图片存对象存储（`STORAGE_BACKEND=local|minio`），DB 存引用与 object key
- ✅ **F-2.3** Item 可在多个 Slot 中存在不同时间段的 `ItemPlacement`（支持历史回溯）
- ✅ **F-2.4** 查询物品：按名称 / 类别 / 上传时间 / 当前 Slot 检索
- ✅ **F-2.5** 删除 Item 前必须先解除所有 active `ItemPlacement`
- ✅ **F-2.6**（新增）**反向录入**：把已有物品直接放进指定 Slot，不经 LLM（`P0.3` 已交付）。
  同一物品的旧 active placement 自动软关闭；「移出」同样是软关闭（`removed_at`），
  行永不物理删除 —— 历史仍可回溯（F-2.3）

### 3.3 AI 识别与推荐

- ✅ **F-3.1** Vision：多模态模型输出结构化识别结果。图片以**内联 data URI** 提交
  （远端模型无法 fetch 本地对象存储的 URL）
- ✅ **F-3.2** 推荐：1～3 个候选 Slot，含依据。**流程分层**：
  确定性候选生成（全部 Slot → ≤ 20）→ 硬规则过滤 → 确定性 Ranking → LLM 对已筛候选精排 + 写理由。
  **LLM 不参与候选生成或约束过滤**
- ✅ **F-3.3** Verifier 是最终安全网；失败可 Retry（≤ 2 次）。Vision 阶段独立 parse-retry ≤ 2 次
- ✅ **F-3.5** 全部 AI 调用记录到 `AgentTrace`（9 步 pipeline + 每步 payload + 耗时）
- ✅ **F-3.6** 冷启动：新用户由 `category → room_type` 默认映射提供兜底
- ⏳ **F-3.4** 用户对推荐的「接受 / 拒绝」反馈**回灌偏好**，影响后续推荐（`P0.4`）
- ⏳ **F-3.7** 每条推荐给出**可读的中文理由**，不含 code / 英文（`P0.4`）

### 3.4 规则与偏好

- ✅ **F-4.1** `UserPreference`：个人偏好（如"我常把工具放在车库"）
- ✅ **F-4.2** `HomeRule`：家庭级规则（"厨房不放过期食品"、"药品上锁"），自然语言 + 结构化字段
- ✅ **F-4.3** 规则作为硬约束或软权重参与推荐
- 📋 规则的用户自定义 UI（当前规则来自 seed，无管理界面）

### 3.5 会话与对话

- ✅ **F-5.1** 助手**已支持多轮**：`conversation_id` + 消息回放（原稿把它排在第二版，实际提前交付）
- 📋 **F-5.2** 对话内直接完成"放置"动作（当前助手只读，给出 CTA 跳转到录入页）

- **NFR-1 性能**：单次识别 + 推荐 P95 ≤ 8s；纯查询 P95 ≤ 300ms
  > ⚠️ 未实测。`P95 ≤ 300ms` 的压测从未做过，不作为已达成项。

- **NFR-7 可测试**：所有核心功能有单元 / 集成 / Agent 测试

## 5. MVP 边界

### 5.1 已交付（Phase 1–13）

- 注册 / 登录（邮箱 + 密码；JWT + Home 选择器 + 自动 provision 家）
- 空间层级**读取 + 写入**（树形视图 / 房间 / 柜子 / 格子；AI 提议 + 手动搭建）
- Item 上传（图片 + 描述）+ Vision 识别 + 模型填表
- 9 步 AI 推荐（候选生成 → 过滤 → 排序 → LLM 精排 → Verifier → Retry）+ 落库
- 推荐确认 → `ItemPlacement`

- 自然语言搜索与助手（多轮、有记忆、能答结构问题）
- `AgentTrace` 记录
- Docker Compose 一键启动；`STORAGE_BACKEND=local` 可在无 MinIO 环境跑通
- 评估 harness + 61 个 golden case

## 7. 风险与开放问题

| 风险 | 应对 |
| --- | --- |
| 多模态模型识别不稳定 | Verifier + 兜底追问（"无法识别时向用户提问"） |
| 推荐结果用户不信任 | 展示「依据」；`P0.4` 的「讲理由」直接针对这一点 |
| **用户不愿意搭建空间结构** | 这是 P0.2 存在的理由：AI 提议 + 用户只做确认 |
| AI 提议的结构「太啰嗦」，用户懒得逐条确认 | 减少单次提议数量；优先提议「层 / 格」而非整个柜子 |
| Slot 容量约束难建模 | 第一版只做「类型 + 软约束」，不做严格物理仿真 |
| 冷启动历史数据不足 | prompt 内注入通用收纳常识 + `category → room_type` 默认映射 |
| 微信小程序迁移成本 | API 与数据结构不含 Web 特定假设 |
